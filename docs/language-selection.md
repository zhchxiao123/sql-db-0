# 语言选型决策记录(ADR)

> 状态:已接受 · 日期:2026-08-15 · 范围:sql-db-0 全仓

## 决策

实现语言:**Python 3(≥3.10,仅标准库,零外部运行时依赖)**。
构建系统:**setuptools(pyproject.toml, PEP 621)**。

## 背景

本仓库的目标是搭建一个 SQL 数据库引擎的实现项目,并接入 sqllogictest 测试框架:

1. 引擎本身:一个从零实现、可执行 SQL 的最小引擎(建表、插入、查询、表达式、聚合等)。
2. sqllogictest runner:能对任意 sqllogictest 测试文件端到端执行,输出机器可读的
   逐条 pass/fail 报告。
3. 测试基座:固定的 sqllogictest 版本/commit 与测试文件清单,由 CI 每次推送自动运行。

候选语言:Python 3、Rust、Go、Node.js。

## 评估

| 维度 | Python 3 | Rust | Go | Node.js |
|------|----------|------|----|---------|
| 外部依赖 | 零(标准库足够) | 需 crates.io 拉取 | 需 module 拉取 | 需 npm 拉取 |
| 构建复杂度 | 低(字节码编译即验证) | 中(cargo build) | 低(go build) | 中(npm install) |
| 迭代速度 | 快 | 慢(编译期) | 中 | 快 |
| 类型安全 | 弱(动态) | 强 | 中 | 弱 |
| 引擎生态先例 | 教学/嵌入式引擎常见 | DuckDB 等新引擎主流 | 有 | 少 |
| 测试基座确定性 | 高(无网络依赖) | 中 | 中 | 中 |

## 理由

1. **零外部依赖 → CI 确定性。** 本里程碑的核心交付是 sqllogictest runner 与测试
   基座。Python 标准库即可完成词法/语法解析、表达式求值、MD5 哈希与 JSON 输出,
   无需在 CI 中拉取任何第三方包,消除网络抖动导致的构建不确定性。Rust/Go/Node
   都需要在 CI 中解析依赖,增加失败面。

2. **迭代速度匹配任务形态。** 引擎与 runner 都是解析器/求值器密集的代码,Python
   的解释执行与 REPL 式调试让"改完即验"的循环最短。本里程碑不涉及性能敏感路径,
   动态类型带来的运行时开销不构成约束。

3. **sqllogictest runner 是验收核心。** 验收标准要求 runner 对任意 sqllogictest
   文件端到端执行并输出逐条报告。Python 的 `unittest` 与标准库足以覆盖该行为的
   全部测试,且测试基座本身即 sqllogictest 格式,与 runner 形成闭环验证。

4. **引擎定位为最小可用实现。** 本里程碑的引擎是"能执行 sqllogictest 测试文件"
   的最小引擎,而非生产级数据库。Python 是此类教学/嵌入式引擎的常见选择,后续若
   需要性能或并发,可再评估用 Rust 重写核心(该决策记录在案,便于追溯)。

5. **构建系统选 setuptools 而非裸脚本。** pyproject.toml 提供标准化的包元数据与
   可安装性;`make build` 以字节码编译作为轻量构建门禁,不引入 `build` 等额外工具。

## 后果

- 正面:CI 无第三方依赖;本地与 CI 行为一致;测试基座可离线运行。
- 负面:引擎性能上限低;动态类型下类型错误在运行时暴露(由 sqllogictest 类型串
  检查兜底)。
- 缓解:runner 对查询结果做类型串(I/R/T/B)一致性校验,把类型错误显式化为
  pass/fail 报告中的失败项。
